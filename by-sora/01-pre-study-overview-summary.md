## 一言でいうと

ISUCONは「速いコードを書く競技」ではなく、**観測 → ボトルネック特定 → 安全に変更 → ベンチで検証**を繰り返す競技。本質のループはこれだけ:

```text
測る → 最大のボトルネックを選ぶ → 小さく変更 → ベンチ → 採用/戻す → また測る
```

## 学ぶ7領域と重要度

領域: ①Linux基礎 ②HTTP/Web ③DB・SQL ④アプリ高速化 ⑤キャッシュ・分散 ⑥計測 ⑦競技運営・チーム戦略

重要度順: **計測 → SQL・DB → アプリコード → キャッシュ → Webサーバー・OS → 複数台**。カーネルの深掘りより「遅いSQLを見つけて直せる」ことが先。

## 各領域の要点

| 領域 | 覚えておくこと |
|------|--------------|
| 競技の流れ | SSH → 構成確認 → 初期ベンチ → 計測 → 特定 → 修正 → ベンチ、の繰り返し。仕様・整合性・再起動・初期化・レギュレーションを壊さない |
| Linux | 「操作できる」より「今何が起きているか読める」。CPU限界/DB待ち/I/O待ち/ロック待ち/外部通信待ちを切り分けられれば十分 |
| HTTP | 優先は Keep-Alive・静的ファイルのNginx直接配信・圧縮のコスト・外部API対策の4つ |
| DB・SQL | **学習の中心**。頻出問題は N+1、インデックス不足（EXPLAINで確認）、SELECT過剰実行、アプリ側集計、トランザクション中の不要処理。判断基準は「総コスト ≒ 平均実行時間 × 実行回数」 |
| アプリ | SQL実行回数 → データ量 → アルゴリズムの順で見る。二重ループはMapで O(N×M)→O(N+M)、ループ内の不変処理は外へ、不要なJSON処理と同期I/Oを消す |
| キャッシュ | 安全な順に、リクエスト内 → プロセスメモリ → Redis → 事前計算。無効化・初期化・複数台での整合性が課題 |
| Nginx | proxy_pass / upstream / keepalive / 静的location あたりを理解。暗記でなく「なぜ詰まっているか」を確認してから変更 |
| 計測 | alp（総処理時間=回数×時間で見る）、pt-query-digest、top/vmstat/iostat、言語プロファイラ（Node.jsなら --prof / Clinic.js） |
| 複数台 | 定石は App+Nginx / App / MySQL の分離。分ければ必ず速くなるわけではない（通信が増える） |
| ベンチ | 検証・整合性チェック付き。手抜きレスポンスは失格。慣れたらベンチマーカーのコードも読む |
| 再起動・構成管理 | 再起動後も動く状態を維持。サーバー上でもGit。**最後の30分に初めて再起動するのは危険** |
| チーム | 計測・指揮 / DB / アプリ・インフラの3分担。ただし全員がボトルネックを理解する。変更ごとにスコア記録、下がった変更は戻す |

## 学習フェーズ（自分がどこにいるか）

1. **最低限動ける** — 過去問起動・ベンチ実行・再起動・ログを読める
2. **SQLで改善できる** — スロークエリ特定・N+1発見・EXPLAIN・インデックス ← **ここまでで戦える**
3. **計測主導で改善できる** — alpで特定、DB/アプリの切り分け
4. **アプリを作り変えられる** — キャッシュ・アルゴリズム・事前計算
5. **複数台を使い切る** — DB分離・複数台・不整合の扱い
6. **競技として完成** — 模擬戦完走・時間管理・再起動試験

実践は「①環境に慣れる → ②SQL縛りで改善 → ③アプリ改善 → ④キャッシュ → ⑤時間制限付き模擬戦（最初は3時間）」の順。

## 後回しでよいもの

カーネルパラメータ網羅、TCP輻輳制御、MySQL内部実装、Redis Cluster、eBPF、SIMD など。まずは **N+1・インデックス・重いエンドポイント・無駄なループ・重複計算** の5つ。
