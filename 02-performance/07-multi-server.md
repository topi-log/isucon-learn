# 2-7. 複数台構成 — 3台を使い切る

> **このドキュメントで学ぶこと**
> - 3台の典型的な役割分担と移行手順
> - CPU コアを使い切る（Node.js のマルチプロセス化）
> - オンメモリキャッシュと複数台の相性問題

初期状態では 1台目だけが働いています。**2台分の計算資源が丸ごと遊んでいる**ので、複数台化は確実に効きます。ただし移行にはリスクがあるので、単発の改善が一段落した中盤〜終盤にやるのが定石です。

## 典型的な最終構成

```
            ベンチマーカー
                 │
                 ▼
   ┌── サーバー1: nginx + アプリ ──┐
   │        │ (upstream振り分け)   │
   │        ▼                     │
   │   サーバー2: アプリ            │
   │        │                     │
   │        └────────┬────────────┘
   │                 ▼
   └────▶ サーバー3: MySQL 専用
```

- **DB は専用サーバーに分離**が最優先。MySQL はメモリ（バッファプール）を大量に使いたいので、アプリと同居させない
- どの構成が最適かは**ボトルネック次第**。DB が重い問題なら「アプリ2台 + DB1台」、アプリCPUが重い問題なら nginx を軽いサーバーに寄せてアプリに専念させる、など計測を見て決める

## 手順1: DB 分離

1. サーバー3の MySQL を外部から接続可能に:

   ```bash
   # /etc/mysql/mysql.conf.d/mysqld.cnf
   # bind-address = 127.0.0.1 → コメントアウト or 0.0.0.0 に変更
   sudo systemctl restart mysql
   ```

2. アプリ用ユーザーがリモート接続を許可されているか確認:

   ```sql
   SELECT user, host FROM mysql.user;
   -- host が 'localhost' のみなら:
   CREATE USER 'isucon'@'%' IDENTIFIED BY 'isucon';
   GRANT ALL ON isuride.* TO 'isucon'@'%';
   ```

3. サーバー1の環境変数（`env.sh` 等、1-5参照）の DB ホストをサーバー3の**プライベートIP**に変更し、アプリ再起動
4. 疎通確認: `mysql -h <サーバー3IP> -u isucon -pisucon isuride -e 'SELECT 1'`
5. ベンチを回してスコアと `top`（両サーバーで）を確認

**注意**: 初期化処理（POST /initialize）がローカルの MySQL を前提にシェルスクリプトを叩いている問題がある。初期化フローがどのサーバーの DB に対して走るのか必ず追うこと。

## 手順2: アプリ2台化

1. サーバー2のアプリの接続先 DB もサーバー3に向ける
2. サーバー1の nginx の upstream にサーバー2を追加（2-6 参照）
3. ベンチで確認

### オンメモリキャッシュとの相性問題 ★重要

アプリを2台にすると、**プロセス内キャッシュ（2-5）がサーバーごとに別物になり、更新が他方に伝わりません**。対策は3つ:

| 対策 | 内容 | 向いている場面 |
|------|------|--------------|
| 不変データだけキャッシュ | 更新されないものは分散しても安全 | まずこれ |
| **エンドポイントを寄せる** | 同じデータを触るAPI群を nginx で同一サーバーに固定（例: 椅子系APIはサーバー2のみ） | ISUCONの定石。状態を持つAPIに有効 |
| 共有ストア (Redis/DB) | キャッシュを外部化 | 手間の割に効果が薄いことも。最後の手段 |

「どのエンドポイントをどのサーバーに置くか」= 「どの状態をどこに持つか」の設計です。移行前にキャッシュしているデータの一覧を書き出して判断しましょう。

## CPU コアを使い切る — Node.js のマルチプロセス化

1プロセスの Node.js は 1コアしか使えません（1-3）。`node` の CPU 使用率が 100% 付近（=1コア分）で張り付いていたら、コア数分のプロセスを立てます。

```typescript
// main.ts の起動部分
import cluster from "node:cluster";
import { availableParallelism } from "node:os";

if (cluster.isPrimary) {
  for (let i = 0; i < availableParallelism(); i++) cluster.fork();
} else {
  await app.listen({ port: 8080 });  // SO_REUSEPORT相当をclusterが処理してくれる
}
```

**注意**: プロセスを分けると、プロセス内キャッシュ・バッファ（2-5 の flush バッファ等）もプロセスごとに分かれます。上の「相性問題」と同じ考慮が必要です。キャッシュ戦略と矛盾する場合は、クラスタ化を諦めて1プロセスに全力させる判断もあり得ます。

## 最終盤のチェックリスト

- [ ] 全サーバーで `sudo systemctl enable` されているか（**再起動試験対策**。enable忘れ=起動しない=失格）
- [ ] 再起動試験のリハーサル: 全台 `sudo reboot` → アプリが自動起動し正常応答するか
- [ ] 計測用のログ（nginx access_log, slow_query_log）を無効化したか
- [ ] 使っていないサービス（他言語の参考実装等）を止めたか
- [ ] ベンチ実行対象のサーバー（ベンチの向き先）指定は正しいか

## 用語集

| 用語 | 意味 |
|------|------|
| スケールアウト / スケールアップ | サーバーの台数を増やす / 1台の性能を上げる。ISUCONは3台固定なので「3台をどう使い切るか」の勝負 |
| DB分離 | MySQLを専用サーバーに移すこと。アプリとメモリ・CPUを奪い合わなくなる。複数台化の第一手 |
| bind-address | MySQLがどのネットワークインターフェースで接続を受けるかの設定。デフォルトはlocalhostのみで、外部から繋ぐには変更が必要 |
| プライベートIP | 同一ネットワーク内でのみ通用するIPアドレス。サーバー間通信はこれを使う（外向きのグローバルIPより速く、無料） |
| GRANT | MySQLのユーザーに権限を与えるSQL。リモート接続には`'user'@'%'`のようにホスト許可も必要 |
| ロードバランス | リクエストを複数のアプリサーバーに振り分けること。nginxのupstreamで実現 |
| エンドポイントを寄せる | 特定のAPI群を特定サーバーに固定で振り分けること。プロセス内キャッシュと複数台を両立させるISUCONの定石 |
| 共有ストア | 複数サーバーから読み書きできる外部のデータ置き場（Redisなど）。キャッシュ共有の最終手段 |
| cluster / availableParallelism | Node.jsの複数プロセス化モジュール / CPUコア数を返す関数。1プロセス1コア制限を突破する |
| SO_REUSEPORT | 複数プロセスが同じポートで待ち受けられるようにするOSの仕組み。clusterが内部で相当の処理をしてくれる |
| 再起動試験 | 競技終了後の全サーバー再起動チェック。`systemctl enable`忘れ・起動順の問題がここで発覚する |
| enable（自動起動） | サーバー起動時にサービスも自動で立ち上がる設定。全サーバー・全サービスで確認する |
