# 1-4. MySQLの基礎

> **このドキュメントで学ぶこと**
> - ISUCON でいじる範囲の MySQL の仕組み（接続・トランザクション・ロック）
> - 競技中によく使う MySQL 操作コマンド
> - 「なぜクエリが遅くなるのか」の下地（詳細は 2-2 へ）

## MySQL の全体像

ISUCON で使う範囲では、MySQL は次のように捉えれば十分です:

```
アプリ ──(TCP 3306 / unix socket)──▶ MySQL サーバー
                                      ├── コネクション管理（max_connections）
                                      ├── SQL パース・実行計画の決定（オプティマイザ）
                                      └── InnoDB ストレージエンジン
                                           ├── バッファプール（メモリ上のキャッシュ）★重要
                                           ├── テーブルデータ + インデックス（B+Tree）
                                           └── トランザクション・行ロック
```

- **バッファプール**: ディスク上のデータをメモリにキャッシュする領域。ここに収まっていればクエリは速い。デフォルト 128MB と小さいので増やすのが定石（→ 2-4）
- **オプティマイザ**: SQL をどう実行するか（どのインデックスを使うか）を決める。その判断を見るのが `EXPLAIN`（→ 2-2）

## 競技中によく使う操作コマンド

```bash
# ログイン（参考実装の認証情報は env ファイルや systemd unit に書いてある）
mysql -u isucon -pisucon isuride

# よく使うSQL
SHOW TABLES;                      -- テーブル一覧
SHOW CREATE TABLE rides\G         -- テーブル定義とインデックスを確認 ★競技序盤に全テーブル分見る
SELECT COUNT(*) FROM rides;       -- 行数の把握（多いテーブル=要注意）
SHOW PROCESSLIST;                 -- いま実行中のクエリ（詰まってるクエリが見える）

-- インデックス追加（最頻出の改善。詳細は 2-2）
ALTER TABLE rides ADD INDEX idx_user_id_created_at (user_id, created_at DESC);
```

`\G` は結果を縦に表示するオプション。横に長い結果を見るときに便利です。

## トランザクションと ACID（ISUCON で必要な範囲）

トランザクションは「複数の更新をまとめて全部成功 or 全部なかったこと」にする仕組み。

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;  -- ここで確定。途中で失敗したら ROLLBACK
```

ISUCON 観点で重要なこと:

1. **トランザクション中に取った行ロックは COMMIT まで保持される**
   - トランザクションを長く開いたまま重い処理（外部API呼び出しなど）をすると、他のリクエストがロック待ちで詰まる
   - → **トランザクションの範囲は最小にする**のが改善パターンの1つ
2. **整合性チェックがあるので、安易にトランザクションを外すのは危険**
   - ベンチマーカーは不整合を検出する。まず他の改善（インデックス等）を優先

## ロックの基礎

InnoDB は**行ロック**（行単位のロック）を使います。

| 操作 | 取るロック |
|------|----------|
| `SELECT` | 基本ロックなし（MVCC で古いスナップショットを読む） |
| `SELECT ... FOR UPDATE` | 対象行の排他ロック |
| `UPDATE` / `DELETE` / `INSERT` | 対象行の排他ロック |

ハマりどころ:

- **インデックスがない列で UPDATE すると、全行スキャンしながら広範囲をロックする**ことがある。インデックスは速度だけでなくロック範囲の面でも重要
- 同じ行を多数のリクエストが同時に UPDATE すると、直列化されて詰まる（例: カウンターの加算）。→ アプリ側でまとめて更新する等の工夫（2-5）

ロック待ちが起きているかは `SHOW PROCESSLIST` で `State` を見る、または:

```sql
SELECT * FROM performance_schema.data_lock_waits\G
```

## コネクションとプール

- アプリからの接続1本 = MySQL 側のコネクション1本
- MySQL の `max_connections`（デフォルト151）を超える接続はエラーになる
- アプリ側プールの `connectionLimit` × プロセス数 ≦ `max_connections` になるよう調整する

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';  -- 現在の接続数
```

## データを覗く習慣をつける

競技序盤に必ずやること:

```sql
-- 各テーブルの行数とデータ量を一覧（information_schema は概算値なので目安）
SELECT table_name, table_rows,
       ROUND((data_length + index_length) / 1024 / 1024) AS size_mb
FROM information_schema.tables
WHERE table_schema = 'isuride'
ORDER BY table_rows DESC;
```

- **行数が多いテーブル**（数十万〜）へのクエリは要注意リスト入り
- 画像バイナリなど**巨大な列**が DB に入っていたら、ファイルに逃がす改善候補（→ 2-4）

## 用語集

| 用語 | 意味 |
|------|------|
| InnoDB | MySQLの標準ストレージエンジン（データの保存・取り出しを担う部分）。行ロックとトランザクションをサポート |
| バッファプール | InnoDBがディスク上のデータをキャッシュするメモリ領域。ここに載っているデータへのアクセスは速い。サイズ調整が定番チューニング |
| オプティマイザ | SQLを「どの順序で・どのインデックスを使って」実行するかを決めるMySQL内部の判断機構 |
| 実行計画 | オプティマイザが決めた実行方法。`EXPLAIN`で確認できる（2-2で詳しく学ぶ） |
| ACID | トランザクションが保証する性質の頭文字（原子性・一貫性・独立性・永続性）。「全部成功か全部なし」＋「確定したら消えない」と押さえればOK |
| COMMIT / ROLLBACK | トランザクションの確定 / 取り消し |
| 行ロック | 特定の行だけを対象にしたロック。InnoDBの基本。テーブル全体を止めないので並行性が高い |
| 排他ロック | 「自分が触っている間、他は読み書き（更新）できない」ロック。UPDATE/DELETE/`SELECT ... FOR UPDATE`が取る |
| MVCC | 更新中でも他のトランザクションが「少し前のスナップショット」を読める仕組み。おかげで通常のSELECTはロック不要 |
| スナップショット | ある時点でのデータの状態のコピー（見え方） |
| デッドロック | 2つのトランザクションが互いのロック解放を待ち合って動けなくなる状態。MySQLは検知して片方を強制ロールバックする |
| max_connections | MySQLが同時に受け付ける接続数の上限。超えるとエラー。アプリ側プール数とセットで調整する |
| information_schema | テーブル定義や統計情報を参照できるメタ情報用データベース |
| `\G` | mysqlクライアントで結果を縦表示にする記法。列が多い結果を見るときに使う |
| LONGBLOB | 巨大なバイナリデータ（画像など）を格納できる列型。DBに入れるとバッファプールを圧迫しがち |
