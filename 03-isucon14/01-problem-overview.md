# 3-1. ISUCON14 問題概要 — ISURIDE

> **このドキュメントで学ぶこと**
> - ISUCON14（2024年12月開催）の問題「ISURIDE」の仕様
> - スコア計算と「ユーザー満足度」の仕組み
> - この問題が要求している設計思想

> 本章の内容は [ISUCON14 問題の解説と講評（公式Blog）](https://isucon.net/archives/58869617.html) と [isucon/isucon14 リポジトリ](https://github.com/isucon/isucon14) に基づきます。

## ISURIDE とは

**自動で動く「椅子」によるライドシェアサービス**。ユーザーがアプリで配車（配椅子）をリクエストすると、椅子がマッチングされ、迎えに来て、目的地まで運んでくれる、という世界観です。

登場人物は3種類で、それぞれ別系統の API を持ちます:

| ロール | 役割 | 主なAPI |
|--------|------|---------|
| **ユーザー (app)** | 椅子に乗る人。ライドを作成し、評価する | ライド作成、通知取得、近くの椅子検索 |
| **椅子 (chair)** | 移動体。位置情報を送り続け、ライドを遂行 | 座標送信、通知取得、ステータス更新 |
| **オーナー (owner)** | 椅子の所有者。売上・稼働状況を見る | 売上集計、椅子一覧 |

## ライドのライフサイクル

```
ユーザーがライド作成 (MATCHING)
   → 椅子がマッチングされる (ENROUTE: 椅子がお迎えに移動)
   → 乗車位置に到着 (PICKUP)
   → ユーザー搭乗、移動開始 (CARRYING)
   → 目的地到着 (ARRIVED)
   → ユーザーが評価を送信 (COMPLETED)
```

このステータス遷移が `ride_statuses` テーブルに**履歴として INSERT されていく**設計になっており、「最新ステータスの取得」が頻発します（→ 2-3 で学んだ「各グループの最新1件」問題）。

## スコア計算

公式解説より:

```
スコア = 実車距離（客を乗せて移動した距離）× 1.0
       + 空車距離（客を乗せず移動した距離）× 0.1
       + 完了したライド数 × 5
```

- **実車移動は空車移動の10倍の価値**。つまり「近くの椅子を割り当てて無駄な移動を減らす」ことがスコアに直結する
- 距離は**マンハッタン距離**（`|緯度の差| + |経度の差|`）で計算される

## ユーザー満足度と成長の仕組み

ベンチマーカーは単なる負荷生成器ではなく「サービスの世界」をシミュレートします:

- ユーザーは以下で**満足度**を評価する:
  1. ライド作成から椅子が割り当たるまでの時間
  2. 割り当たった椅子の現在地から乗車位置までの距離
  3. 理想の移動時間と実際の移動時間の差
- 満足度が高いと**ユーザーが定着し、口コミで新規ユーザーが増える** → 負荷（=スコアの機会）が増える
- 逆に遅い・待たせるサービスはユーザーが離脱して伸びない

さらに、ベンチマーカーの世界は **30ms 刻み（tick）で動いており、「全エンドポイントが 30ms 以内に応答する」ことが理想目標**とされました。

## この問題が要求している設計思想

ISURIDE の特徴は、単発の最適化テクニックの寄せ集めでは伸びにくいことです:

1. **スループットだけでなく「ビジネスロジックの質」が問われる**
   - マッチングアルゴリズム（誰にどの椅子を割り当てるか）自体がスコアを左右する
   - 「速くする」と「賢く割り当てる」の両輪
2. **エンドポイント同士が相互依存**
   - 椅子の座標送信が速くなる → 椅子が速く動ける → ライドが速く完了 → スコア増、のように改善が連鎖する
3. **明確な単一ボトルネックがなく、解法が複数ある**
   - 公式講評でも「SSE 化しなくても JSON API + 適切なキャッシュで10万点以上に到達できた」と明言されており、王道を丁寧に積み上げれば戦える

## 参考実装のデータモデル（主要テーブル）

| テーブル | 内容 | 注意点 |
|---------|------|--------|
| `users` / `owners` / `chairs` | 各ロールの基本情報 + アクセストークン | 認証で毎回引かれる |
| `rides` | ライド本体（乗車位置・目的地・chair_id） | |
| `ride_statuses` | ステータス遷移の**履歴** | 最新1件の取得が頻発 |
| `chair_locations` | 椅子の位置情報の**履歴**（座標送信のたびINSERT） | 膨張する。距離集計が重い |
| `coupons` / `payment_tokens` | クーポン・決済トークン | |

「履歴テーブルから最新値/集計値を毎回計算する」という 2-4 パターンAの構図が2箇所（ride_statuses, chair_locations）に仕込まれているのがわかります。

## 用語集

| 用語 | 意味 |
|------|------|
| ISURIDE | ISUCON14の問題。自動で動く「椅子」によるライドシェア（配車）サービス |
| ライドシェア | 移動したい人と乗り物をマッチングするサービス形態（Uberなどが実例） |
| ライド | 1回の乗車リクエスト〜完了までの単位。ISURIDEの中心概念 |
| マッチング | 待っているライドに空いている椅子を割り当てる処理 |
| ステータス遷移 | ライドの状態が MATCHING → ENROUTE → PICKUP → CARRYING → ARRIVED → COMPLETED と進むこと |
| ライフサイクル | あるデータ（ライド）が生成されてから完了するまでの一連の流れ |
| マンハッタン距離 | `\|x1−x2\| + \|y1−y2\|` で計算する距離。碁盤の目の道を進む距離のイメージ。ISURIDEの距離はすべてこれ |
| 実車 / 空車 | 客を乗せて移動 / 乗せずに移動。スコア係数が1.0と0.1で10倍違う |
| tick（ティック） | ベンチマーカーの世界が進む時間の最小単位。ISUCON14は30ms刻みだった |
| 満足度 | ベンチ内のユーザーがサービスを評価する内部指標。高いとユーザーが増え、負荷（=得点機会）が増える |
| 口コミによる成長 | 満足度が高いと新規ユーザーが増えるベンチマーカーの仕組み。「速さがビジネス成長に直結する」ことのシミュレーション |
| アクセストークン | ログイン済みユーザー/椅子を識別する文字列。毎リクエストの認証でDB検索される |
| ULID風のID（VARCHAR(26)） | 時刻順に並ぶ26文字のID形式。ISURIDEの主キーに使われている |
