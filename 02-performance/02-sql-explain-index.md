# 2-2. EXPLAINとインデックス設計 ★最重要章

> **このドキュメントで学ぶこと**
> - インデックス（B+Tree）の仕組みと「なぜ速くなるのか」
> - EXPLAIN の読み方（type / rows / Extra のどこを見るか）
> - 複合インデックスの設計ルールとよくある間違い

ISUCON で最も費用対効果の高い改善がインデックス追加です。`ALTER TABLE` 1行でスコアが数倍になることも珍しくありません。この章は手を動かして身につけてください。

## インデックスがないと何が起きるか

```sql
SELECT * FROM rides WHERE user_id = 'abc123';
```

`user_id` にインデックスがないと、MySQL は**テーブルの全行を先頭から読んで**条件に合う行を探します（フルテーブルスキャン）。100万行あれば100万行読む。ベンチ中はこれが毎秒何百回も走るので、DB の CPU が焼き切れます。

## インデックス（B+Tree）の仕組み

インデックスは「**その列の値でソートされた索引**」です。本の索引と同じ:

```
インデックス idx_user_id (user_id) のイメージ:

  user_id でソート済みの木構造
        [ m ]
       /     \
   [a-l]     [m-z]
   /  \       /  \
 a,abc,... 　...  ...
  │
  └─ 各エントリは「本体の行の場所」を指している
```

- ソート済みなので**二分探索**で目的の値に一発で辿り着ける: 100万行でも約20回の比較で済む（log₂ 100万 ≒ 20）
- **範囲検索**（`BETWEEN`, `>`, `<`）と**ソート**（`ORDER BY`）にも効く: ソート済みの索引を順に読むだけでいいから

### タダではない

- INSERT/UPDATE のたびにインデックスも更新される → 書き込みが少し遅くなる
- とはいえ ISUCON では読み取りが支配的なことが多く、**必要なインデックスを張らないデメリットの方が圧倒的に大きい**。「張りすぎのコスト」は後で考えれば良い

## EXPLAIN — オプティマイザの実行計画を見る

クエリの頭に `EXPLAIN` を付けるだけ:

```sql
EXPLAIN SELECT * FROM rides WHERE user_id = 'abc123' ORDER BY created_at DESC\G
```

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: rides
         type: ALL            ← ★ここ
possible_keys: NULL
          key: NULL           ← ★ここ
         rows: 985231         ← ★ここ
        Extra: Using where; Using filesort   ← ★ここ
```

### 見るべき4項目

**① type — アクセス方法（左ほど良い）**

| type | 意味 | 評価 |
|------|------|------|
| `const` / `eq_ref` | 主キー・ユニークキーで1行特定 | 最高 |
| `ref` | インデックスで絞り込み | 良い。通常はこれを目指す |
| `range` | インデックスで範囲検索 | 良い |
| `index` | インデックス全体をスキャン | 微妙 |
| `ALL` | **フルテーブルスキャン** | ★危険。行数が多いなら即改善対象 |

**② key — 実際に使われたインデックス**。`NULL` なら何も使われていない。

**③ rows — 読むと見積もられた行数**。この数字が実態の絞り込み後の行数に近いほど良い。「1件返すクエリなのに rows: 985231」は異常。

**④ Extra — 補足情報**

| Extra | 意味 |
|-------|------|
| `Using index` | ★良い。インデックスだけで完結（カバリングインデックス、後述） |
| `Using filesort` | ★注意。ORDER BY のために別途ソートしている → インデックスで解決できないか検討 |
| `Using temporary` | ★注意。一時テーブル作成（GROUP BY 等で発生） |
| `Using where` | 読んだ後に WHERE で絞っている（それ自体は普通） |

## インデックスの張り方

```sql
-- 単一列
ALTER TABLE rides ADD INDEX idx_user_id (user_id);

-- 複合（複数列）
ALTER TABLE rides ADD INDEX idx_user_created (user_id, created_at DESC);

-- 確認
SHOW CREATE TABLE rides\G
```

## 複合インデックスの設計ルール

ISUCON で差がつくのはここです。実際のクエリはたいてい「絞り込み + ソート」の組み合わせだからです。

### ルール1: 左端から使われる（最重要）

複合インデックス `(a, b, c)` は「a でソート、a が同じなら b でソート、…」という電話帳（姓→名の順）のような構造です。

| クエリ | `(a, b, c)` は効くか |
|--------|---------------------|
| `WHERE a = ?` | ✅ 効く |
| `WHERE a = ? AND b = ?` | ✅ 効く |
| `WHERE b = ?` | ❌ 効かない（左端 a を飛ばせない） |
| `WHERE a = ? ORDER BY b` | ✅ 効く（絞った範囲が b でソート済み） |
| `WHERE a > ? AND b = ?` | △ a の範囲検索までしか使えない |

→ **「等値条件の列を左に、範囲・ソートの列を右に」**が基本形。

### ルール2: WHERE + ORDER BY をセットで解決する

ISUCON 頻出のクエリパターン:

```sql
-- 「このユーザーの最新のライドを取る」
SELECT * FROM rides WHERE user_id = ? ORDER BY created_at DESC LIMIT 1;
```

- `idx(user_id)` だけ → 絞り込みは速いが、その後 filesort が走る
- `idx(user_id, created_at DESC)` → **絞り込んだ範囲が既にソート済み**。先頭1件読んで終わり。filesort が消える

ISUCON14 でも `(chair_id, updated_at DESC)` のようなインデックスが定石でした。

### ルール3: カバリングインデックス

SELECT する列がすべてインデックスに含まれていると、**テーブル本体を読まずインデックスだけで応答**できます（Extra: `Using index`）。

```sql
SELECT id, created_at FROM rides WHERE user_id = ?;
-- idx(user_id, created_at, id) があれば本体アクセス不要
```

超頻出クエリに対しての最終手段として覚えておくと強い。

### よくある間違い

```sql
-- ❌ 列に関数や計算を適用するとインデックスが使えない
WHERE DATE(created_at) = '2026-07-26'
-- ✅ 範囲条件に書き換える
WHERE created_at >= '2026-07-26' AND created_at < '2026-07-27'

-- ❌ 中間一致 LIKE はインデックス不可
WHERE name LIKE '%isu%'
-- （前方一致 'isu%' なら使える）

-- ❌ (a) と (a, b) の両方を張る — (a, b) があれば (a) は不要（左端ルールより）
```

## 実戦手順（競技中のワークフロー）

1. pt-query-digest（2-1）の Rank 上位クエリをコピー
2. `EXPLAIN` にかける → `type: ALL` や `filesort` を確認
3. WHERE の等値列 → 範囲/ORDER BY 列の順で複合インデックスを設計して `ALTER TABLE`
4. もう一度 `EXPLAIN` → `type: ref`、rows 激減、filesort 消滅を確認
5. ベンチを回してスコアと pt-query-digest の順位変動を確認

**注意**: 初期データにしかインデックスは張られない問題がほとんどなので、`ALTER TABLE` は**初期化処理（POST /initialize 等）で毎回実行されるSQLファイルに追記**するか、事前に流しておく運用をチームで決めること。ベンチのたびに DB が初期化される問題では、初期化SQLに入れないと消えます。

## 用語集

| 用語 | 意味 |
|------|------|
| インデックス | 特定の列の値でソートされた索引データ。検索・ソートを高速化する。本の巻末索引のイメージ |
| B+Tree（ビープラスツリー） | インデックスの実装に使われる木構造。何億行あっても少ない回数の比較で目的の値に辿り着ける |
| 二分探索 | ソート済みデータを半分ずつ絞って探す方法。100万件でも約20回の比較で見つかる |
| フルテーブルスキャン | インデックスを使わずテーブル全行を読むこと。EXPLAINの`type: ALL`。行数が多いと致命的 |
| EXPLAIN | クエリの前に付けると、実行せずに実行計画（どう実行するつもりか）を表示するSQL |
| type（ALL / ref / range / const / eq_ref） | EXPLAINのアクセス方法。ALLが最悪（全行）、refは「インデックスで絞り込み」で通常の合格ライン |
| possible_keys / key | 使える候補のインデックス / 実際に使われたインデックス。keyがNULLなら索引なしで実行される |
| rows | 読むと見積もられた行数。返す件数に対して極端に大きければ改善余地あり |
| Using filesort | ORDER BYのために読み込み後に別途ソートしている状態。インデックスで解決できることが多い |
| Using temporary | 一時テーブルを作って処理している状態。GROUP BYなどで発生。重い兆候 |
| Using index | インデックスだけで応答できている状態（カバリングインデックス）。良い状態 |
| 複合インデックス | 複数列を組み合わせたインデックス。`(a, b)`は「aでソート、同値ならbでソート」の電話帳構造 |
| 左端ルール（最左プレフィックス） | 複合インデックスは左の列から順にしか使えないという制約。`(a, b)`は`WHERE b = ?`単独には効かない |
| カバリングインデックス | SELECTする列が全部インデックスに含まれていて、テーブル本体を読まずに済む状態 |
| 前方一致 / 中間一致 | `LIKE 'abc%'` / `LIKE '%abc%'`。前方一致はインデックスが効くが中間一致は効かない |
| ALTER TABLE | テーブル定義の変更SQL。インデックス追加（ADD INDEX）に使う |
| 初期化処理（/initialize） | ベンチ開始時にDBを初期状態に戻す処理。追加したインデックスはここに組み込まないとベンチごとに消える問題がある |
