## ISUCONでの知識の全体像

ISUCONは、単に「高速なコードを書く競技」ではありません。**初見のWebサービスを観測し、現在のボトルネックを特定し、安全に変更し、ベンチマークで効果を検証する競技**です。公式の過去問解説でも、「モニタリングやコードリーディングでボトルネックを発見し、解消していくゲーム」と説明されています。([ISUCON公式Blog](https://isucon.net/))

学ぶべきことは次の7領域に分かれます。

1. Linux・サーバーの基礎
2. HTTP・Webアプリケーション
3. データベース・SQL
4. アプリケーションの高速化
5. キャッシュ・並行処理・分散構成
6. 計測・プロファイリング
7. 競技運営・チーム戦略

重要度は「**計測 → SQL・DB → アプリケーションコード → キャッシュ → Webサーバー・OS → 複数台構成**」の順。最初からLinuxカーネルの細かい設定を学ぶより、まずは**遅いSQLを発見して直せること**のほうが圧倒的に重要です。

## 1. 競技そのものを理解する

典型的な競技の流れ:

```text
SSH接続 → 構成確認 → 初期ベンチ → 計測（アクセスログ・DBログ・CPU）
→ 最大のボトルネック特定 → 修正 → 再起動 → ベンチ → スコア・エラー確認 → 次のボトルネックへ
```

改善対象は、SQL、アプリケーションコード、Nginx、MySQL、キャッシュ、ファイル配信、サーバー間の役割分担、OS設定、起動スクリプトなど。ただし何でも変更すればよいわけではなく、「仕様を壊さない／整合性チェックを通す／再起動後も動く／初期化処理を壊さない／レギュレーションを守る」という制約があります。

公式では過去問のソースコードと構築方法が公開されており、ISUCON14では競技者VM 3台とベンチマーカー環境を含む構成が公開されています。まず過去問を実際に起動することが、最も重要な入り口です。([環境構築の案内](https://isucon.net/archives/54946542.html))

## 2. Linux・サーバー基礎

知らないサーバーに入り、その場で状態を調査します。Linuxを「操作できる」だけでなく、**現在何が起きているかを読み取れること**が必要です。

最低限、自然に使える状態を目指すコマンド:

```bash
ps aux / top / htop / free -h / df -h / du -sh / ss -lntp / lsof
journalctl / systemctl / grep / awk / sed / sort / uniq / xargs / find / tail -f
```

- **プロセス確認** (`ps aux`, `systemctl status`, `journalctl -u`): どのアプリが・どのユーザーで動き、起動コマンド・ログの場所・再起動方法は何かを確認する
- **ポート確認** (`ss -lntp`): 80=nginx, 3000=app, 3306=mysql, 6379=redis のような対応を把握する
- **CPU・メモリ・I/O** (`top`, `free -h`, `vmstat 1`, `iostat -x 1`): user/system CPU、idle、iowait、load average、page cache、swap、ディスクI/O、コンテキストスイッチなどの概念を理解する

ただし最初からすべてを深く学ぶ必要はなく、まずは「**CPUが限界なのか／DB待ちなのか／ディスクI/O待ちなのか／ロック待ちなのか／外部通信待ちなのか**」の判断ができれば十分です。

## 3. HTTPとWebアプリケーション

リクエストの経路（ベンチマーカー → Nginx → アプリケーション → MySQL/Redis/ファイル → レスポンス）を理解します。

学ぶべきHTTP知識: メソッド、ステータスコード、ヘッダー、Cookie、セッション、Keep-Alive、gzip、Cache-Control、ETag、Range Request、WebSocket、Server-Sent Events。全部を一度に覚える必要はなく、優先度が高いのは:

- **Keep-Alive**: 接続を毎回作り直さず再利用する。接続確立が大量に発生している場合、パフォーマンスに影響する
- **静的ファイル**: 画像・CSS・JSをアプリ経由で返しているなら、Nginxから直接返すことで負荷を下げられる可能性がある
- **圧縮**: レスポンスが大きい場合はgzipが効くが、圧縮自体にもCPUコストがある
- **外部API**: タイムアウト、接続再利用、並列化、キャッシュ、呼び出し回数削減を検討する

## 4. データベースとSQL

ここがISUCON学習の中心で、初心者が最もスコアを伸ばしやすい領域です。最初に理解するもの: SELECT / WHERE / JOIN / GROUP BY / ORDER BY / LIMIT / サブクエリ / 集約関数 / トランザクション / インデックス / 実行計画。

### 4.1 N+1クエリ

ユーザー一覧を取得したあと、一人ずつ投稿を取得するコード:

```ts
const users = await findUsers();
for (const user of users) {
  user.posts = await findPostsByUserId(user.id);
}
```

ユーザーが100人なら合計101回のSQLが発生します。JOIN、IN句、一括取得などに変えます。

```sql
SELECT * FROM posts WHERE user_id IN (?, ?, ?, ...);
```

### 4.2 インデックス不足

`SELECT * FROM posts WHERE user_id = ? ORDER BY created_at DESC` が大量に実行されているなら、候補は `CREATE INDEX idx_posts_user_id_created_at ON posts(user_id, created_at)`。

ただし闇雲に作らず `EXPLAIN` で実行計画を確認します。見るべき項目は type / possible_keys / key / rows / Extra。特に `ALL`、`Using filesort`、`Using temporary` を見ますが、これらが出たら必ず遅いわけではなく、テーブルサイズや実行回数も含めて判断します。

### 4.3 SELECTの過剰実行

1回10msのSQLでも、1リクエスト中に100回呼ばれれば1秒。「1回あたりの遅さ × 実行回数」の両方を見て、**総コスト ≒ 平均実行時間 × 実行回数** で改善効果を考えます。

### 4.4 アプリケーション側での集計

大量の行を取得してからアプリで集計しているなら、DB側の `GROUP BY` 集計のほうが効率的な場合があります。一方で、同じ集計を大量に繰り返すなら事前集計やメモリ上のMapが有効なことも。「常にDBに任せる」ではなく、**データ転送量／SQL実行回数／DB負荷／アプリ負荷／再利用可能性**を比較して決めます。

### 4.5 トランザクションとロック

学ぶべきもの: BEGIN/COMMIT/ROLLBACK、行ロック、`SELECT ... FOR UPDATE`、ロック待ち、デッドロック、分離レベル、トランザクション範囲。

典型的な問題は、トランザクション中に不要な処理（外部API呼び出し・ファイル処理など）をしていること。外部APIが遅い間もロックを保持する可能性があるため、可能なら外部API呼び出しをトランザクションの外（前）に出します。ただし整合性要件を壊さないことが前提です。

## 5. アプリケーションコードの高速化

言語そのものの細かい最適化よりも、まずアルゴリズムとデータアクセスを見ます。優先順位は「SQL実行回数 → データ量 → アルゴリズム → I/O回数 → シリアライズ → オブジェクト生成 → 言語固有の最適化」。

- **二重ループ**: ユーザーN × 投稿M の照合ループは O(N×M)。Map を作れば O(N+M) にできる

  ```ts
  const postsByUserId = new Map<number, Post[]>();
  for (const post of posts) {
    const values = postsByUserId.get(post.userId) ?? [];
    values.push(post);
    postsByUserId.set(post.userId, values);
  }
  for (const user of users) {
    user.posts = postsByUserId.get(user.id) ?? [];
  }
  ```

- **同じ計算の繰り返し**: ループ内で毎回 `await loadConfig()` のような不変処理をしているならループ外に出す
- **不要なJSON処理**: 大きなオブジェクトの `JSON.stringify()`/`JSON.parse()` はCPUとメモリを消費する。レスポンスに不要な項目を含めていないか、同じJSONを何度も生成していないか確認する
- **同期処理**: Node.jsなら `readFileSync`/`writeFileSync`、同期的な暗号処理、CPU負荷の高いループがイベントループを塞ぐ。Goなら goroutine の過剰生成、lock競合、チャネル待ち、GC負荷を見る

## 6. キャッシュ

キャッシュは強力ですが、雑に導入するとバグの原因になります。種類ごとの特徴:

- **リクエスト内キャッシュ**: 同じリクエスト中の重複取得を防ぐ。比較的安全
- **プロセスメモリキャッシュ** (`const globalCache = new Map()`): 高速だが、複数プロセス・複数サーバーでは共有されず、サーバーAとBのキャッシュが別々になる。更新との整合性に注意
- **Redis**: 複数プロセス・サーバー間で共有できるが、RedisアクセスもネットワークI/O。「MySQLよりは軽いがローカルメモリよりは重い」ので何でも入れればよいわけではない
- **事前計算**: 「読み取り時にCOUNT」から「書き込み時にcounterを加算、読み取り時はcounterを取得」へ。読み取りが非常に多い場合に有効だが、更新漏れ・二重加算・初期化処理・トランザクション整合性が難しくなる

## 7. Nginx・Webサーバー

Nginxの主な役割: リバースプロキシ、静的ファイル配信、gzip、アクセスログ、TLS終端、負荷分散。

```nginx
upstream app {
    server 127.0.0.1:3000;
}
server {
    listen 80;
    location / {
        proxy_pass http://app;
    }
}
```

理解すべき項目は `proxy_pass` / `upstream` / `access_log` / `keepalive` / `worker_processes` / `worker_connections` / `sendfile` / 静的ファイル用の `location`。ただし設定値を暗記するのではなく、「**なぜ今の構成で詰まっているのか**」を確認してから変更します。

## 8. 計測とプロファイリング

ISUCONで最も重要な能力です。勘で修正するのではなく「仮説 → 計測 → 変更 → 再計測」を繰り返します。

- **アクセスログ (alp)**: URLごとにリクエスト数・平均/最大/合計応答時間・ステータスコードを集計する。重要なのは平均だけではない。`/api/users` 10ms×10000回=100秒 と `/api/admin` 500ms×10回=5秒 なら、遅いのは後者だが総負荷が大きいのは前者。**総処理時間 = 回数 × 1回あたりの時間**で見る
- **MySQLスロークエリログ (pt-query-digest)**: 実行回数・合計/平均/最大時間・Rows examined・Rows sent を見る。「1回10秒のQuery A」より「1回10ms×10万回のQuery B」のほうが総負荷が大きい可能性がある
- **システム全体** (`top`, `vmstat 1`, `iostat -x 1`, `pidstat 1`): CPU・メモリ・ディスクI/O・プロセス単位の負荷を確認する
- **言語プロファイラ**: Go=pprof（CPU/heap/mutex/goroutine profile）、Node.js=CPU profile / heap snapshot / `--prof` / Clinic.js系 / event loop delay、Ruby=stackprof等、Python=cProfile等。最初は使用言語を一つに固定して学ぶ

あなたの場合は普段の経験から、まず**Node.js / TypeScriptかGo**に絞るのが自然です。ただしISUCONでは、TypeScriptではなく配布されたJavaScript実装を直接触る場合や、ビルド時間を考慮する必要があります。

## 9. 複数台構成

近年の過去問では複数台構成もあり、ISUCON14の公開環境では競技者VMが3台でした。([isucon/isucon14](https://github.com/isucon/isucon14))

役割分担の例: 「サーバー1: Nginx+App / サーバー2: App / サーバー3: MySQL」または「サーバー1: エンドポイントA / サーバー2: エンドポイントB / サーバー3: MySQL」。

学ぶべきこと: Nginxロードバランシング、DB接続先の変更、bind address、firewall、サーバー間通信、セッション共有、ローカルキャッシュの不整合、ファイル共有、データの永続性、単一障害点。**複数台に分ければ必ず速くなるわけではなく**、アプリとDBを分けることでネットワーク通信が増えて逆に遅くなる場合もあります。

## 10. ベンチマークの読み方

ベンチマーカーは単なる負荷試験ではなく、「大量リクエスト送信＋レスポンス検証＋整合性検査＋スコア化」を行います。レスポンスの省略・DB更新の省略・キャッシュを返し続ける、だけでは整合性チェックに失敗します。

過去問にはベンチマーカーの実装が含まれることがあります（例: [isucon9-qualify](https://github.com/isucon/isucon9-qualify)）。最終的にはベンチマーカーのコードも読み、「どのエンドポイントが何回呼ばれるか／どの処理がスコアに寄与するか／何をすると失格になるか」を理解できるようにします。ただし初心者の段階ではアプリ側のログ分析を優先して構いません。

## 11. 再起動試験と構成管理

動いているプロセスだけ変更しても不十分で、**サーバー再起動後も変更が反映される**状態にします。管理対象: ソースコード、systemd設定、Nginx設定、MySQL設定、起動スクリプト、環境変数、DBスキーマ、インデックス、初期化処理、権限、シンボリックリンク。

本番サーバー上でもGit（status/diff/add/commit/log）を使い、変更前後の差分と復旧地点を作ります。また競技の途中から定期的に `systemctl restart` で各サービスを再起動してベンチが通ることを確認します。**最後の30分に初めて再起動すると、復旧できず終了する危険があります。**

## 12. チーム戦略

ISUCONは技術だけでなく、分担と意思決定の競技でもあります。3人チームの例:

- **メンバーA（計測・指揮）**: ベンチ実行、アクセスログ分析、SQL分析、スコア記録、優先順位管理
- **メンバーB（DB担当）**: SQL確認、N+1解消、インデックス、クエリ変更、MySQL設定
- **メンバーC（アプリ・インフラ担当）**: アプリコード、キャッシュ、Nginx、複数台構成、systemd

ただし完全分業すると知識が分断されます。理想は「主担当は決める、しかし全員が現在のボトルネックを理解する」。

変更ごとにスコアを記録します。**スコアが下がった変更を惰性で残さないことが重要です。**

| 時刻 | 変更 | スコア | エラー | 判断 |
|------|------|--------|--------|------|
| 10:15 | 初期状態 | 1,200 | なし | 基準 |
| 10:40 | index追加 | 3,800 | なし | 採用 |
| 11:10 | キャッシュ追加 | 2,900 | なし | 戻す |
| 11:30 | N+1解消 | 7,200 | なし | 採用 |

## 13. 学習優先順位（6フェーズ）

| フェーズ | 目標 | 学ぶこと |
|---------|------|---------|
| **1. 最低限動ける** | 過去問を起動・SSH・ベンチ実行・再起動・ログを読める | Linux基本操作、systemd、Nginx、MySQL接続、Git、HTTPの基本、過去問環境構築 |
| **2. SQLで改善できる** | スロークエリ特定、N+1発見、EXPLAIN、インデックス追加、実行回数削減 | インデックス、複合インデックス、JOIN、GROUP BY、実行計画、スロークエリログ、pt-query-digest、トランザクション、ロック |
| **3. 計測主導で改善できる** | alpで重いエンドポイント発見、DB/アプリの切り分け、修正前後の説明 | アクセスログ、percentiles、throughput、latency、CPU使用率、iowait、プロファイラ、flame graph |
| **4. アプリ全体を作り変えられる** | キャッシュの安全な導入、アルゴリズム改善、事前計算化、I/O削減 | Mapによる計算量改善、バッチ取得、メモリキャッシュ、Redis、非同期処理、コネクションプール、JSONシリアライズ、GC |
| **5. 複数台を使い切る** | DB/アプリ分離、アプリ複数台化、エンドポイント分割、不整合の扱い | Nginx upstream、ロードバランシング、DBネットワーク設定、複数プロセス/サーバー、レプリケーション基礎、分散整合性 |
| **6. 競技として完成させる** | 8時間の模擬戦完走、衝突しない変更、再起動後も動く、安全な最終状態 | チーム分担、Git運用、スコア記録、チェックリスト、時間管理、撤退判断、再起動試験、バックアップ |

フェーズ2まで到達すれば、初心者としてかなりISUCONらしい戦い方ができます。

## 14. おすすめの実践カリキュラム（5段階）

1. **環境に慣れる**: 過去問を起動 → 初期ベンチ → 構成を図にする → ログ場所を調べる → 再起動 → コードを一行変更して反映。スコアは上げなくてよい
2. **SQLだけで改善する**: 「Nginx設定変更禁止・キャッシュ禁止・複数台化禁止、SQLとインデックスだけ変更可」と縛り、スロークエリログ・実行回数・N+1・EXPLAIN・インデックスだけで改善する。最も重要なDBチューニングに集中できる
3. **アプリコードを改善する**: 二重ループ、重複クエリ、重複計算、過剰なデータ取得、不要なシリアライズ、同期I/Oを探す。変更ごとに「なぜ速くなると思ったか／実際に何が変わったか／スコアはいくつ変わったか」を記録する
4. **キャッシュを使う**: リクエスト内キャッシュ → プロセスメモリキャッシュ → Redis → 事前集計の順で試し、それぞれ「更新時の無効化／初期化後の正しさ／複数台での正しさ／メモリ使用量」を確認する
5. **時間制限付き模擬戦**: 最初は3時間でよい（構成把握30分 → DB改善60分 → アプリ改善45分 → キャッシュ・Nginx 25分 → 再起動試験・最終確認20分）。慣れたら本番に近い時間で解く

## 15. 最初は後回しでよいもの

Linuxカーネルパラメータの網羅、TCPの細かい輻輳制御、MySQL内部実装の完全理解、Redis Cluster、高度なレプリケーション構成、eBPF、SIMD、アセンブリ、言語ランタイムの極端な最適化。

まずは「N+1を見つける／インデックスを張る／重いエンドポイントを見つける／無駄なループを消す／同じ計算を繰り返さない」ことのほうが大切です。

```text
    │     │     │    │     │     │    │     │     │
 Linux  HTTP   計測  SQL  App  Infra  分担  Git  時間管理
                │     │     │
              alp   index cache
              top   N+1   algorithm
              slow  lock  I/O削減
              log
```

本質的なループは「**測る → 最大のボトルネックを選ぶ → 小さく変更する → ベンチマークする → 採用または元に戻す → もう一度測る**」。

ISUCONの勉強は、知識を順番に暗記するより、**過去問を動かしながらこのループを何度も回すこと**が中心になります。最初の具体的な学習順は「Linux操作 → Webアプリのリクエスト経路 → SQL・インデックス → アクセスログとスロークエリ → アプリのアルゴリズム → キャッシュ → Nginx → 複数台 → 模擬戦」がよいです。
