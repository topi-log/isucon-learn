# 1-1. ISUCONとは何か

> **このドキュメントで学ぶこと**
> - ISUCON という競技のルールとスコアの決まり方
> - 当日8時間で何が起きるか（タイムライン）
> - 「何をすると勝てるのか」の全体像

## ISUCON とは

**I**ikanjini **S**peed **U**p **Con**test。
LINEヤフー社が主催する、**与えられた Web サービスを制限時間内（8時間）にどれだけ高速化できるか**を競うコンテストです。

- チームは最大3人（1人参加も可）
- 各チームに同一スペックのサーバーが **3台** 支給される（クラウド上）
- サーバー上には「遅い状態の Web アプリケーション」がデプロイ済み
- 複数言語の参考実装（Go / Ruby / Node.js / Python / PHP / Rust など）が用意されており、**好きな言語に切り替えて競技できる**

## スコアの決まり方

主催者が用意した**ベンチマーカー**が、実際のユーザーの行動を模したリクエストを大量に送りつけます。

```
スコア ≒ 制限時間内に正しく処理できたリクエスト（シナリオ）の量
```

重要なポイント:

1. **正しく**動くことが前提。レスポンスの内容が間違っているとベンチマーカーの整合性チェックで失格（fail）になる。高速でも間違っていたら 0 点
2. ベンチマーカーは「速いサーバーにはより多くの負荷をかける」挙動をする。つまり速くすればするほどスコアが伸びる余地が生まれる
3. 問題ごとに独自のスコア計算がある（例: ISUCON14 は「椅子が客を乗せて移動した距離」で加点。詳細は Part 3）

**最終スコアは競技終了後の再起動試験・追試を通ったものだけが有効**。競技終了時にアプリが起動しない・データが消える状態だと失格になるため、「再起動しても動く」ことの確認が必須です。

## 当日のタイムライン（典型例）

| 時刻 | やること |
|------|---------|
| 10:00 | 競技開始。マニュアル（当日発表のルール・仕様書）を読む |
| 10:00-11:00 | 初期セットアップ: ssh 設定、コードを git 管理下に、計測ツール導入、初回ベンチ実行 |
| 11:00-12:00 | 計測結果からボトルネック特定。インデックス追加など確実に効く改善から着手 |
| 12:00-16:30 | 「計測 → 改善 → ベンチ → 計測」のループをひたすら回す |
| 16:30-17:30 | 大きな変更は止める。複数台構成の最終化、ログ・監視ツールの無効化、再起動試験 |
| 18:00 | 競技終了 |

## 何をすると勝てるのか（改善の典型パターン）

過去問を通じて頻出する改善は、実はかなりパターン化されています。本ドキュメントの Part 2 はこのリストの各項目に対応しています。

| 改善 | 効果 | 対応章 |
|------|------|--------|
| スロークエリに**インデックスを張る** | 絶大。ほぼ毎回必須 | 2-2 |
| **N+1 クエリ**の解消 | 絶大。ほぼ毎回登場する | 2-3 |
| 静的ファイルを nginx から配信 | 大 | 2-6 |
| 重い計算結果・マスタデータの**キャッシュ** | 大 | 2-5 |
| 画像などを DB でなくファイルで持つ | 大（問題による） | 2-4 |
| **複数台構成**（DB を別サーバーへ等） | 大。終盤の定石 | 2-7 |
| バルクINSERT・不要な処理の削除 | 中〜大 | 2-4, 2-5 |

## チームでの役割分担（参考）

3人チームの典型:

- **アプリ担当**（1〜2人): コードを読み、N+1 解消やキャッシュ実装
- **インフラ担当**（1人): 計測ツールの整備、nginx/MySQL 設定、複数台構成、デプロイフロー

1〜2年目で初参加なら、まず**アプリ担当として「計測結果を見てクエリとコードを直せる」状態**を目指すのが現実的です。本ドキュメントもそこに主眼を置いています。

## 用語集

| 用語 | 意味 |
|------|------|
| ベンチマーカー | 主催者が用意した負荷試験プログラム。実際のユーザー行動を模したリクエストを大量に送り、処理量からスコアを算出する |
| 参考実装 | 主催者が複数言語で用意した同一機能のアプリケーションコード。チームは好きな言語の実装を選んで改善していく |
| 整合性チェック | ベンチマーカーがレスポンス内容の正しさを検証すること。速くても内容が間違っていれば失格になる |
| fail（フェイル） | 整合性チェック違反やアプリのエラーによりベンチが失敗し、スコアが無効（0点）になること |
| デプロイ | 変更したコードをサーバーに配置して動かすこと。ISUCONでは「編集→転送→ビルド→再起動」の一連の流れを指す |
| 再起動試験 | 競技終了後、運営がサーバーを再起動しても正常に動作するかを確認する試験。通らないと失格 |
| インデックス | DBの検索を高速化する索引。詳細は 2-2 で学ぶ |
| N+1（クエリ） | ループの中で1件ずつSQLを発行してしまう性能問題の定番パターン。詳細は 2-3 |
| 静的ファイル | 画像・CSS・JavaScriptなど、リクエストによって内容が変わらないファイル |
| キャッシュ | 一度計算・取得した結果を保存しておき、次回以降は保存済みの値を使い回すこと |
| バルクINSERT | 複数行を1回のSQLでまとめて挿入すること。1件ずつより大幅に速い。詳細は 2-4 |
| ロードバランス | 複数のサーバーにリクエストを振り分けて負荷を分散すること |
