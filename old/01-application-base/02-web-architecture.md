# 1-2. Webアプリケーションの構成

> **このドキュメントで学ぶこと**
> - ISUCON で与えられるサーバー構成の典型形
> - 1つの HTTP リクエストがどこを通ってレスポンスになるか
> - 「ボトルネック」とは何か、なぜ1箇所ずつしか直せないのか

## ISUCON の典型的な初期構成

競技開始時、3台のうち **1台目にすべてが載っている**のが典型です。

```
                 サーバー1台目
┌─────────────────────────────────────────┐
│                                         │
│  :443/:80                               │
│  ┌───────┐    ┌──────────────┐    ┌───────┐
│  │ nginx │ →  │ アプリケーション │ →  │ MySQL │
│  └───────┘    │ (Node.js など) │    └───────┘
│   リバース     └──────────────┘     データ保存
│   プロキシ      ビジネスロジック
│                                         │
└─────────────────────────────────────────┘
     サーバー2台目・3台目は遊んでいる（もったいない → 2-7 で使う）
```

各コンポーネントの役割:

| コンポーネント | 役割 | ISUCONでの主な仕事 |
|--------------|------|------------------|
| **nginx** | リバースプロキシ。外からのリクエストを受けてアプリに転送 | 静的ファイル配信、アクセスログ出力（計測に使う） |
| **アプリ** | ビジネスロジック。ルーティング、SQL発行、レスポンス生成 | N+1解消、キャッシュなど改善の主戦場 |
| **MySQL** | データの永続化 | インデックス、スキーマ改善の主戦場 |

## リクエストの一生

`GET /api/users/123` が処理される流れを追うと:

```
クライアント
  │ ① TCP/TLS 接続 + HTTP リクエスト
  ▼
nginx
  │ ② プロキシ転送 (localhost:8080 や unix socket へ)
  ▼
アプリ (Node.js)
  │ ③ ルーティング → ハンドラ関数の実行
  │ ④ SQL 発行「SELECT * FROM users WHERE id = 123」
  ▼
MySQL
  │ ⑤ クエリ実行（インデックスがないと全行スキャン！）
  ▲ ⑥ 結果セットを返す
アプリ
  │ ⑦ 結果を JSON に整形
  ▼
nginx → クライアントへレスポンス
```

**この①〜⑦のどこかに時間がかかっている箇所（ボトルネック）がある**。ISUCON はそれを見つけて潰す競技です。

経験上、時間の内訳は圧倒的に **⑤ MySQL のクエリ実行**が大きいことが多く、次いで「⑤を何度も繰り返す」N+1（④⑤×N回）、その次にアプリの CPU 処理です。

## レイテンシとスループット

混同しやすい2つの指標:

- **レイテンシ (latency)**: 1リクエストにかかる時間。例: 「このAPIは1回 200ms かかる」
- **スループット (throughput)**: 単位時間に処理できるリクエスト数。例: 「毎秒 500 リクエスト捌ける」

ISUCON のスコアは基本的に**スループット**で決まりますが、ベンチマーカーは「レスポンスが遅いとユーザーが離脱する」ようにできていることが多く、**レイテンシを下げるとスループットが上がる**構造になっています。

## ボトルネックの鉄則

システム全体の速度は**一番遅い箇所**で決まります。水道管のイメージ:

```
太い管 ── 太い管 ──【細い管】── 太い管
                     ↑
        ここを太くしない限り、他をいくら太くしても流量は増えない
```

これが意味すること:

1. **ボトルネックでない箇所を改善してもスコアは1点も上がらない**
   - 例: DB が限界なのに nginx をチューニングしても無意味
2. **ボトルネックは移動する**
   - DB を速くしたら次はアプリの CPU がボトルネックになる、を繰り返す
3. だから**毎回計測し直す**必要がある（→ 2-1）

## ISUCON 頻出の構成変更

初期構成から、競技中に典型的にはこう変えていきます（詳細は 2-6, 2-7）:

```
最終形の例:
  サーバー1: nginx + アプリ
  サーバー2: アプリ (nginx から振り分け)
  サーバー3: MySQL 専用
```

- 静的ファイル（画像・JS・CSS）はアプリを通さず nginx が直接返す
- DB を専用サーバーに分離して、アプリと CPU/メモリを奪い合わないようにする
- アプリを2台に増やして nginx でロードバランス

## 用語集

| 用語 | 意味 |
|------|------|
| リバースプロキシ | クライアントからのリクエストを最初に受け取り、後ろのアプリサーバーへ転送する中継サーバー。nginx が代表例 |
| nginx（エンジンエックス） | 高速なWebサーバー/リバースプロキシソフトウェア。ISUCONではほぼ毎回登場する |
| ミドルウェア | OSとアプリの間で共通機能を提供するソフトウェア（nginx、MySQLなど）。※Webフレームワークの「ミドルウェア関数」とは別物なので注意 |
| TCP | ネットワーク通信の基盤プロトコル。接続を確立してからデータをやり取りする |
| TLS | 通信を暗号化するプロトコル。HTTPSのSの部分。接続確立（ハンドシェイク）にコストがかかる |
| ルーティング | 「このURLパスとHTTPメソッドの組はこの処理関数へ」という振り分けの仕組み |
| ハンドラ | 特定のエンドポイントへのリクエストを処理する関数 |
| エンドポイント | APIの窓口1つ1つ。`GET /api/users/:id` のような「メソッド + パス」の単位 |
| 全行スキャン（フルスキャン） | テーブルの全行を先頭から読んで条件に合う行を探すこと。行数が多いと極端に遅い |
| レイテンシ | 1リクエストの処理にかかる時間。「応答までの待ち時間」 |
| スループット | 単位時間あたりに処理できるリクエスト数。ISUCONのスコアはほぼこれで決まる |
| ボトルネック | システム全体の速度を制限している最も遅い箇所。ここ以外を改善しても速くならない |
| JSON | データ交換フォーマット。Web APIのレスポンスの標準形式 |
