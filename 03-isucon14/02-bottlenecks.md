# 3-2. ISUCON14 ボトルネック分析

> **このドキュメントで学ぶこと**
> - ISURIDE 初期実装の主要ボトルネック6つ
> - それぞれが Part 2 のどのパターンに対応するか

初期実装のボトルネックを、公式解説・講評で挙げられたものを中心に整理します。**先に 3-1 を読んでいる前提**です。各ボトルネックがどの学習章のパターンかを対応付けているので、「過去問は既習パターンの組み合わせ」であることを実感してください。

## ① インデックスがほぼ存在しない初期状態

**症状**: ほぼすべてのテーブルに主キー以外のインデックスがなく、あらゆるクエリがフルスキャン。

- `users.access_token` / `chairs.access_token` — **認証ミドルウェアで毎リクエスト**フルスキャン
- `ride_statuses (ride_id, created_at)` — 最新ステータス取得のたびにフルスキャン + filesort
- `chair_locations (chair_id, created_at)` — 最新位置取得で同上

→ **対応パターン: 2-2（インデックス設計）**。pt-query-digest を回せば上位が全部これ。

## ② 通知エンドポイントのポーリング負荷

**症状**: ユーザー・椅子はそれぞれ通知エンドポイント（`GET /api/app/notification`, `GET /api/chair/notification`）をポーリングして自分のライド状態を知る。ベンチの世界は 30ms 刻みで動くため、**極めて高頻度に叩かれる**。1回1回が重いクエリ（最新ライド + 最新ステータスの取得）を実行するため、塵積型の最大ボトルネックになる。

レスポンスに含まれる `retry_after_ms`（次のポーリングまでの間隔指示）を大きくすれば負荷は減るが、**通知が遅れる = ユーザー満足度が下がる**というトレードオフが設計されている。

→ **対応パターン: 2-1（alp で塵積型を特定）+ 2-5（キャッシュ）**。alp で SUM 1位になる典型。

## ③ マッチング処理が「500msに1件・ランダム」

**症状**: ライドと椅子のマッチングは `isuride-matcher` という定期実行処理が担うが、初期実装は:

- **500ms に1回**しか動かない
- 1回につき**1件のライド**しか処理しない
- 空いている椅子を**ランダムに**割り当てる（距離を見ない）

結果: ライドが積み上がって待ち時間が伸び（満足度低下）、遠くの椅子が割り当たって空車移動が増える（×0.1 の距離ばかり稼ぎ、実車 ×1.0 の機会を失う）。

→ **対応パターン: Part 2 に直接対応なし。「アプリケーションロジックの改善」**。ISUCON14 の独自性が最も出た部分（改善は 3-3 で詳述）。

## ④ chair_locations 履歴テーブルと距離集計

**症状**: 椅子が座標を送るたびに `chair_locations` へ INSERT され、テーブルが膨張し続ける。その上で:

- 最新位置の取得が `ORDER BY created_at DESC LIMIT 1`
- オーナー画面の**総移動距離**の計算が、**全履歴を引いて隣接レコード間の距離を合算**する重量級クエリ

→ **対応パターン: 2-4 パターンA（履歴テーブル → 最新値テーブル + 書き込み時に累積距離を差分更新）**。

## ⑤ N+1 だらけの一覧系エンドポイント

**症状（公式解説で名指しされた例）**:

- `GET /api/app/nearby-chairs`（近くの椅子検索）: **全椅子を取得してから、1台ずつ**最新ライド・最新ステータス・最新位置を個別クエリで確認する **2N+1 構造**
- `GET /api/owner/chairs`: **全椅子の総移動距離を計算してから**オーナーで絞り込む（絞り込みが後ろにある）

→ **対応パターン: 2-3（N+1解消: ウィンドウ関数・IN句一括化）**。「絞ってから計算する」順序の入れ替えも重要。

## ⑥ 椅子の座標送信 `POST /api/chair/coordinate` のブロッキング

**症状**: 椅子はこのエンドポイントの**応答が返るまで次の移動をしない**。つまりこの API のレイテンシがそのまま椅子の移動速度 = 実車距離 = スコアに直結する。初期実装は毎回同期的に INSERT + ステータス確認クエリを実行。

仕様上「位置情報の反映は3秒までの遅延が許容」と定められていた。

→ **対応パターン: 2-5（非同期化・バッファリング + バルクINSERT）+ 2-4**。「マニュアルの許容遅延を読み取って非同期化する」という ISUCON の王道が最も綺麗に決まる箇所。

## まとめ: ボトルネック × 学習章の対応表

| # | ボトルネック | 種別 | 対応章 |
|---|------------|------|--------|
| ① | インデックス皆無 | DB | 2-2 |
| ② | 通知ポーリング | 塵積型・キャッシュ | 2-1, 2-5 |
| ③ | マッチング (500ms/1件/ランダム) | アプリロジック | 3-3 |
| ④ | 位置履歴テーブルと距離集計 | スキーマ設計 | 2-4 |
| ⑤ | nearby-chairs 等の N+1 | N+1 | 2-3 |
| ⑥ | 座標送信のブロッキング | 非同期化 | 2-5 |

公式講評は「複数の解決パスがあり、単一の明白なボトルネックはない」「個々のエンドポイントのレイテンシより全体のスループット（相互作用）が重要」と総括しています。①⑤のような定石と、③⑥のような問題固有ロジックの理解、その両方が必要な良問でした。

## 用語集

| 用語 | 意味 |
|------|------|
| ポーリング | クライアントが「変化ないか？」と定期的にサーバーへ問い合わせ続ける方式。回数が多いと塵積型の負荷になる |
| 通知エンドポイント | ユーザー/椅子が自分のライド状態を知るためにポーリングするAPI。ISUCON14最大の負荷源の1つ |
| retry_after_ms | 通知レスポンスに含まれる「次のポーリングまで待つ時間」の指示。大きくすると負荷減・通知遅延増のトレードオフ |
| 2N+1 | 「全件取得1回 + 各件につき2クエリ」の構造。N+1の悪化版。nearby-chairsが該当した |
| filesort | ソート用インデックスがなく、読み込んだ後に別途ソートしている状態（2-2参照） |
| マッチング処理（matcher） | ライドと椅子を割り当てる定期実行プログラム。初期実装は500msに1件・ランダムだった |
| ランダム割り当て | 距離を考慮せず空き椅子を選ぶこと。遠い椅子が割り当たり空車距離（×0.1）ばかり増える |
| ブロッキング | 処理の完了を待って次に進めない状態。椅子は座標送信の応答を待ってから動くため、応答速度が椅子の移動速度を決めた |
| 許容遅延（3秒ルール） | 「位置情報の反映は3秒まで遅れてよい」という仕様。非同期化してよい根拠 |
| 塵積型（ちりつも型） | 1回は軽いが回数が膨大なため合計で最大の負荷になるパターン（2-1参照）。通知エンドポイントが典型 |
| 相互依存 / 改善の連鎖 | あるAPIの高速化が別の指標（椅子の移動速度→実車距離→スコア）に波及する構造。ISUCON14の特徴 |
